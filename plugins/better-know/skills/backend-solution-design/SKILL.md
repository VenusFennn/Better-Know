# 后端解决方案设计

## 目标

基于只读调查，为后端 Bug 修复、新功能添加、旧功能修改和旧功能优化输出完整、正确、可执行、可验证的解决方案。

本技能只输出方案，不实施代码、数据、配置或基础设施变更。技能被调用即表示当前任务停留在方案阶段；不得把方案阶段扩展为实现、迁移或发布阶段。

## 不可违反的边界

允许：

- 阅读源码、架构文档、API 与事件契约、数据库结构、迁移文件和已有测试；
- 搜索调用关系、数据流、状态变化和副作用链路；
- 查看 Git 历史、脱敏日志、Trace、指标和已有诊断结果；
- 查看不会改变业务状态的接口响应和运行状态；
- 执行不会写入项目、改变数据、安装依赖或影响线上负载的已有只读诊断。

禁止：

- 修改、创建、删除、格式化或批量重写项目文件；
- 修改测试文件；
- 安装或升级依赖；
- 修改配置、环境变量、数据库、缓存、消息或业务数据；
- 执行数据库迁移、数据回填或消息重放；
- 调用具有业务副作用的接口；
- 对线上系统执行压测、故障注入或无界查询；
- 提交、推送、创建 PR、发布或部署；
- 把计划中的实现、迁移或测试描述成已经完成。

访问生产日志、数据、密钥或受保护环境必须具有明确授权。只读不等于无风险，应控制数据敏感性、查询范围和系统负载。

无法在只读条件下确认的事实必须标记为“待验证假设”，并说明它可能如何改变方案。

## 固定五步框架

0. 建立事实基线，明确现象、目标、领域不变量、证据和能力缺口。
1. 双向分析上游生产者、中间处理、状态与副作用以及下游消费者。
2. 定义约束、非目标和可验证验收标准。
3. 基于领域边界、正确参考、契约与 SSOT 设计完整方案。
4. 通过反证、故障推演、兼容推演和测试设计完成方案自验。

五步不可跳过，但每一步的分析深度应与用户影响、数据风险、影响范围、不可逆性、系统复杂度和当前不确定性相匹配。

## 给方案前必答的五个问题

1. 要改什么、为什么改，涉及哪个领域规则或系统能力？
2. 它牵连哪些上游生产者、中间处理、状态、副作用和下游消费者？
3. 有没有语义相同且经过验证的正确参考实现，权威契约和 SSOT 在哪里？
4. 约束、非目标和验收标准是什么？
5. 哪些失败、并发、重试、兼容或迁移场景可能推翻方案，应如何验证？

五个问题必须得到实质回答，但不要求机械输出固定问答。简单任务可以合并表述，复杂任务应展开影响链、方案取舍和验证映射。

## 事实与证据纪律

明确区分：

- 已验证事实；
- 基于证据的推断；
- 为继续分析采用的工作假设；
- 尚未解决且会实质影响方案的歧义。

不得虚构文件、函数、接口、表结构、事件、配置、日志、指标、测试结果、部署拓扑或 Git 历史。只有证据支持时，才能给出具体文件、符号和实施落点。

## 分析方式

- 优先使用业务要求、API 或事件契约、领域模型、数据约束和项目架构规则；
- 参考既有实现前，先验证其业务语义、输入输出、故障语义、约束和质量要求是否一致；
- 沿“上游生产者 → 接入与转换 → 应用与领域逻辑 → 状态和副作用 → 下游消费者”进行双向影响分析；
- 识别同一业务事实是否在多处重复维护，以及应收敛还是保持领域隔离；
- 对与任务相关的事务、并发、幂等、兼容、迁移、安全、容量和可观测性给出结论；不相关的维度不必机械展开；
- 调查到足以安全实施即可停止，不为了形式完整无限读取无关代码。

## 跨前后端协作

当任务同时涉及前端和后端时：

- 本技能只对后端领域给出专业子方案，不单独宣称已经完成全栈方案；
- 后端负责领域不变量、外部契约、数据所有权、权限、事务、副作用、兼容和后端验证；
- 后端不决定具体页面布局和交互表现，但必须提供足以让前端正确表达业务状态的稳定字段、枚举、错误分类和状态语义；
- API、事件、字段、枚举、错误语义和版本兼容属于跨端契约，必须分析现有和新旧前端消费者；
- 需要前端配合的内容必须明确写成契约影响、兼容要求或待确认事项，不虚构前端实现；
- 与前端子方案出现冲突时，列出冲突、双方证据和收敛条件，不得忽略或任选一方；
- 跨端任务的统一结论、发布顺序和端到端验证交由 `fullstack-solution-design` 汇总。

建立跨端覆盖关系：

```text
用户需求
→ 前端体验与输入
→ 跨端契约
→ 后端领域、数据与副作用
→ 联合验收与端到端验证
```

## 方案可读性

默认假设读者理解业务但不熟悉当前代码库。方案必须先说明用户可理解的业务含义，再给出精确技术标识：

- 关键且不透明的函数、类、Controller、Service、Repository、数据对象、字段、表、Topic、文件和术语第一次出现时，在相邻位置说明它是什么、负责什么，以及必要时为什么与当前问题有关；
- 文件路径、类名、方法名、表名和 Topic 不得裸列；不得只输出修改对象清单；
- 事务、幂等、Outbox、Saga、CQRS 等术语必须说明它们在当前任务中解决的具体业务或故障问题；
- 解释必须来自源码、调用关系、测试、文档、契约或运行证据，推断必须明确标注；
- 保留原始技术标识供开发者搜索，后续重复出现时使用稳定中文短称，不反复解释；
- 多个关键对象集中出现时，可在当前章节动态增加“关键对象说明”表；对象较少时使用行内解释；
- 不解释与任务无关的代码对象，不把方案扩展成框架或分布式系统教程；
- 七个顶层章节和动态子章节规则保持不变。

## 输出要求

最终方案必须保留以下七个顶层标题：

1. 结论；
2. 事实与根因；
3. 双向影响面；
4. 约束、非目标和验收标准；
5. 详细解决方案；
6. 测试与验证方案；
7. 风险与待确认事项。

七个顶层标题固定，二级及以下内容必须根据任务实际范围动态生成：

- 纯后端任务只输出后端生产者、领域逻辑、状态、副作用、消费者、方案和测试，不输出前端影响、前端方案、前端测试或跨端发布等无关小节；
- 只有证据表明存在前端消费者或需要修改跨端契约时，才展开前端依赖、跨端契约、兼容和发布顺序；
- 数据迁移、缓存、消息、并发、安全、性能、灰度、回滚和混合版本等内容只在相应风险被触发时展开；
- 不输出空的二级标题，也不使用批量“无”“不适用”占位；
- 某个固定顶层章节内容较少时，用一段有实质信息的结论表达，不为填充格式增加无关分析。

最终方案根据任务复杂度调整篇幅，并在七段式中覆盖：

- 当前行为、目标行为、证据、根因或能力缺口；
- 上游生产者、中间处理、状态与副作用、下游消费者、隐性依赖和 SSOT；
- 约束、非目标和可验证验收标准；
- 推荐方案、架构落点、契约、数据流或状态流及确定性实施步骤；
- 任务相关的兼容、迁移、灰度、可观测和回滚设计；
- 正常、失败、边界和主要回归路径的测试与验证设计；
- 具体风险和会实质影响实施的待确认事项。

跨前后端任务还必须输出后端职责、对前端消费者的契约影响、兼容和发布要求，以及需要全栈方案协调的事项。

建立以下覆盖关系：

```text
需求或问题
→ 方案改动
→ 验收标准
→ 测试或验证
```

任何需求没有对应方案，或者任何验收没有对应验证，都表示方案尚未完成。

## 测试设计责任

- 只设计测试，不修改测试，也不声称修复后测试已经通过；
- 根据失败模式选择单元、性质、契约、集成、迁移、并发、故障注入、安全、性能或端到端测试；
- Bug 回归测试在合理可行时应体现“旧实现失败，按方案修复后通过”；
- 覆盖率用于发现遗漏，不单独证明测试质量；项目已有覆盖率门禁时必须遵守，没有依据时不擅自规定统一覆盖率；
- 如某种测试不适用，说明原因和下一种最有区分能力的验证方式。

## 方案自验

输出前主动尝试推翻方案：

- 是否只处理接口表象，没有修复领域根因；
- 是否遗漏重要生产者、消费者或外部副作用；
- 是否错误复用了 Legacy 实现；
- 是否破坏 API、事件或数据兼容；
- 是否遗漏前端消费者对字段、枚举、状态、错误和时序语义的依赖；
- 是否把具体页面表现错误地固化为后端领域规则；
- 是否出现没有职责说明的关键函数、类、分层对象、表、Topic 或专业术语；
- 是否为了通俗而删除了开发者实施所需的精确技术标识；
- 是否引入双写、双轨状态或第二套事实来源；
- 事务、并发、幂等、重试和部分失败是否可能破坏方案；
- 缓存与权威数据是否可能发散；
- 数据迁移是否支持混合版本、失败恢复和回滚；
- 权限、租户和敏感数据边界是否安全；
- 方案是否能在目标容量和依赖故障下成立；
- 是否存在更小但同样完整的方案；
- 是否依赖未经确认的业务假设；
- 测试是否真的能够识别目标错误。

只检查与当前任务具有合理因果关系的风险，不机械套用全部检查项。

## 停止规则

满足以下条件后停止调查并输出方案：

- 已能可靠解释当前状态、根因或能力缺口；
- 已形成足以安全实施的双向影响模型；
- 已明确领域权威来源、架构落点和主要副作用；
- 已明确约束、验收和关键失败边界；
- 已形成可执行的实施、兼容、迁移或发布步骤；
- 已设计能够证明结果的测试；
- 进一步只读调查不太可能实质改变方案。

若缺少的信息会改变领域语义、数据模型、外部契约、迁移策略或不可逆风险，应提出最小且明确的待确认问题并停在方案阶段。
