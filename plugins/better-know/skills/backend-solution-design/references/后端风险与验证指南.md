# 后端风险与验证指南

## 使用方式

本指南是《后端解决方案方法论》的条件参考，不是每个任务都必须逐项执行的检查表。

先根据任务识别触发条件，再只读取和应用对应章节：

| 触发条件 | 需要读取的章节 |
|---|---|
| 新增或修改 API、RPC、事件、错误语义 | 一、契约与版本兼容 |
| 修改数据库结构、索引、约束或历史数据 | 二、数据模型与迁移 |
| 一个业务操作包含多个状态变化或外部副作用 | 三、事务、并发与一致性 |
| 接收重试请求、重复消息、回调或可重入任务 | 四、幂等、重复与顺序 |
| 使用消息队列、事件总线、Outbox 或异步工作流 | 五、消息与异步流程 |
| 使用缓存、读模型、搜索索引或物化视图 | 六、缓存与派生数据 |
| 调用数据库之外的远程服务或第三方系统 | 七、外部依赖与弹性 |
| 涉及认证、授权、多租户、敏感数据或管理入口 | 八、安全与信任边界 |
| 目标包含延迟、吞吐、容量、资源或稳定性 | 九、性能、容量与稳定性 |
| 涉及定时任务、过期、时区或长流程 | 十、时间、调度与后台任务 |
| 变更风险需要灰度、观测、回滚或临时兼容 | 十一、发布、可观测与清理 |

同一任务可以触发多个章节。未触发的章节不必为了显得全面而展开。

---

## 一、契约与版本兼容

### 需要回答

- 契约的生产者、所有者和消费者是谁；
- 变化的是字段形态、业务语义、错误语义还是时序保证；
- 新增字段是否可选，缺省值含义是什么；
- 删除、重命名、类型变化或枚举扩展会影响哪些消费者；
- 未知字段和未知枚举值如何处理；
- 调用方能否区分业务拒绝、参数错误、认证失败、限流、依赖失败和系统错误；
- 哪些错误可重试，重试是否安全；
- 新旧生产者和消费者是否会同时存在；
- 是否需要版本化、能力协商、兼容适配或弃用窗口；
- 临时兼容何时删除，谁负责确认消费者已经迁移。

### 常见失败模式

- HTTP 状态码不变但业务语义改变；
- 新增必填字段导致旧调用方失败；
- 枚举扩展使旧消费者进入不可达分支；
- 错误被统一映射成可重试错误，引发重试风暴；
- 事件字段重命名但历史消息仍在队列；
- 服务端先删除旧字段，消费者尚未升级；
- 序列化格式兼容，但字段含义已经不兼容。

### 验证设计

- Provider 和 Consumer 契约测试；
- 新生产者对旧消费者、旧生产者对新消费者的兼容矩阵；
- 正常、缺失、未知、非法和扩展字段；
- 各类错误与调用方行为；
- 版本协商、降级和弃用告警；
- 历史事件或存量请求样本回放，但不得在生产环境产生副作用。

## 二、数据模型与迁移

### 需要回答

- 目标数据语义和约束是什么；
- Schema 变化是新增、收紧、拆分、合并还是删除；
- 新旧代码和新旧数据是否会同时存在；
- 迁移是否采用“先扩展、再迁移、后收敛”；
- 新字段如何初始化，历史数据如何处理；
- 回填是否幂等、可分批、可限速、可暂停和可恢复；
- 脏数据如何发现、记录和处置；
- 大表 DDL、索引构建和回填是否可能锁表、占满磁盘或放大复制延迟；
- 约束何时启用，启用前如何确认存量数据满足；
- 代码回滚时，旧版本能否理解新数据；
- 迁移完成后如何验证一致性并删除临时字段和兼容逻辑。

### 常见失败模式

- 同一发布同时执行不兼容 DDL 和代码切换；
- 新代码假设回填已完成，但回填仍在进行；
- 双写两处数据但没有一致性检查和退出条件；
- 回填失败后重跑产生重复或覆盖新数据；
- 默认值只存在于 ORM，不存在于数据库；
- 新索引构建导致写入阻塞或资源耗尽；
- 代码回滚后无法读取已经写入的新格式；
- 删除字段前没有确认所有消费者和任务停止使用。

### 推荐阶段

根据风险选择：

1. 扩展：增加向后兼容的 Schema、字段或接口；
2. 兼容：代码同时理解新旧表示，建立必要观测；
3. 迁移：分批回填或转换，记录进度和异常；
4. 切换：将权威读写路径切到目标表示；
5. 验证：比较数量、约束、抽样和业务不变量；
6. 收敛：停止双写，删除临时兼容和旧结构。

这些阶段不是固定发布次数，小型迁移可以合并，但不能省略其安全责任。

### 验证设计

- 空库、代表性历史数据和脏数据；
- 迁移首次执行、重复执行、中断和恢复；
- 新旧代码与新旧数据兼容矩阵；
- 回填前后总量、唯一性、引用关系和领域不变量；
- 大数据量下的时间、锁、磁盘、复制延迟和失败窗口；
- 回滚代码后的数据可读性；
- 临时机制清理后的最终状态。

## 三、事务、并发与一致性

### 需要回答

- 哪些状态必须原子地一起变化；
- 事务边界是否覆盖领域不变量，而不是机械覆盖整个请求；
- 是否跨数据库、缓存、消息或第三方形成多资源一致性问题；
- 并发写采用乐观锁、悲观锁、唯一约束、原子操作还是串行化；
- 冲突如何被检测、返回和重试；
- 隔离级别是否允许脏读、不可重复读、幻读或写偏差影响目标不变量；
- 事务内是否存在慢远程调用或长时间计算；
- 进程在提交前后崩溃时留下什么状态；
- 系统要求强一致、读己之写、单调读还是最终一致；
- 最终一致的窗口、补偿和用户可见行为是什么。

### 常见失败模式

- 先调用第三方成功，后提交数据库失败，无法回滚副作用；
- 数据库提交成功，消息发布失败，消费者永远不知道变化；
- 读取后更新没有版本条件，导致丢失更新；
- 只在应用层检查唯一性，并发请求绕过检查；
- 扩大事务范围造成锁等待和吞吐下降；
- 在事务中自动重试非幂等逻辑；
- 使用“最终一致”描述没有恢复机制的永久不一致。

### 验证设计

- 多个线程或进程同时更新同一业务对象；
- 提交前、提交后、消息发布前后和外部调用前后的故障点；
- 冲突检测、重试次数和最终响应；
- 不同隔离级别下的目标异常；
- 事务回滚后数据库、缓存、消息和外部副作用状态；
- 恢复任务或补偿完成后领域不变量成立。

---

## 四、幂等、重复与顺序

### 需要回答

- 哪些入口可能被调用方、代理、队列、调度器或人工操作重复触发；
- “相同业务操作”如何识别；
- 幂等键由谁生成，作用域、存储位置和有效期是什么；
- 同一键但请求内容不同如何处理；
- 幂等记录与业务提交是否保持一致；
- 成功响应是否可安全重放；
- 失败后重试是继续、重做还是返回已有结果；
- 事件是否要求顺序，顺序范围是全局、聚合、租户还是分区；
- 陈旧事件和版本冲突如何识别；
- 去重记录过期后再次到达会怎样。

### 常见失败模式

- 只在内存中去重，多实例或重启后失效；
- 幂等记录先提交，业务事务失败，后续请求永远被错误拦截；
- 使用请求时间作为幂等键，无法稳定识别业务操作；
- 相同键携带不同金额或对象仍返回旧结果；
- 消费者确认消息后才发现业务提交失败；
- 假设队列严格有序，但扩容或重试改变顺序；
- 去重 TTL 小于消息最长重试窗口。

### 验证设计

- 相同请求串行和并发重复；
- 相同键不同载荷；
- 首次处理成功但响应丢失后的重试；
- 处理中崩溃后的再次投递；
- 去重记录写入和业务写入之间的故障；
- 新旧事件乱序、重复和延迟到达；
- 多实例、重启和超过 TTL 后的行为。

---

## 五、消息与异步流程

### 需要回答

- 消息代表事实、命令还是通知；
- Topic、分区键和消费者组如何定义；
- 投递保证是至多一次、至少一次还是其他模型；
- 生产与本地事务如何协调，是否需要 Outbox；
- 消费成功的确认点在哪里；
- 消费者是否幂等；
- 是否依赖顺序，顺序范围是什么；
- 重试策略、退避、最大次数和死信处理是什么；
- Poison Message 如何隔离；
- 消费积压、重复、延迟和失败如何观测；
- 事件 Schema 如何演进；
- 补偿和人工处置如何执行并审计。

### 常见失败模式

- 数据库提交和消息发布之间存在丢失窗口；
- 消费者在业务提交前确认消息；
- 无限立即重试压垮下游；
- 一个坏消息阻塞整个分区；
- 死信队列有数据但没有处理责任；
- 事件包含数据库当前状态而非发生事实，重放语义不稳定；
- 消费者依赖全局顺序，但分区无法保证；
- 修改事件字段后无法处理队列中的历史消息。

### 验证设计

- 发布成功、失败和进程崩溃；
- 消费成功但确认失败造成的重复；
- 处理失败、退避、最大重试和死信；
- 分区内外乱序；
- 历史 Schema 与新消费者；
- 积压恢复和批量重放；
- Outbox 轮询、重复发布和清理；
- 指标、Trace 和告警能够定位卡在哪个阶段。

---

## 六、缓存与派生数据

### 需要回答

- 权威数据源是什么；
- 缓存保存原始事实还是派生表示；
- Key 是否包含租户、权限、版本和业务维度；
- 采用 Cache-Aside、Write-Through、Write-Behind 还是其他策略；
- 写数据库和失效缓存的顺序是什么；
- TTL、主动失效和版本校验如何配合；
- 可接受的陈旧窗口是什么；
- 缓存失效失败如何恢复；
- 击穿、穿透、雪崩和热点如何处理；
- 读模型、搜索索引和物化视图如何重建和校验；
- 权限变化后缓存是否仍可能泄露旧权限数据。

### 常见失败模式

- 更新数据库后删除缓存失败，旧值长期存在；
- 先删除缓存再写数据库，并发读把旧值重新写回；
- Key 缺少租户或权限范围，造成跨边界数据泄露；
- 缓存被当成权威来源但没有持久恢复能力；
- 所有 Key 同时过期形成流量尖峰；
- 负缓存使新创建数据在一段时间内不可见；
- 搜索和读模型没有重建或差异检测机制。

### 验证设计

- 命中、未命中、过期和失效失败；
- 并发读写和陈旧值回填；
- 数据库更新与缓存操作各阶段故障；
- 租户、权限和版本维度隔离；
- 热点、批量过期和回源容量；
- 权威数据与缓存、索引、读模型之间的差异检测和重建。

---

## 七、外部依赖与弹性

### 需要回答

- 调用是查询、命令还是不可逆副作用；
- 超时预算如何在调用链分配；
- 哪些失败可重试，哪些不可重试；
- 重试由哪一层负责，如何避免多层重试放大；
- 调用是否幂等，超时后是否可能实际成功；
- 限流、熔断、隔离和背压策略是什么；
- 降级结果是否满足业务语义；
- 部分成功如何记录、恢复和告知调用方；
- 第三方配额、速率和错误契约如何观测；
- 依赖恢复后如何补偿或追赶。

### 常见失败模式

- 没有超时，线程或连接被长期占用；
- SDK、服务和网关三层同时重试，形成指数放大；
- 对支付、发送或创建操作盲目重试；
- 熔断器把业务拒绝统计为系统故障；
- 降级返回空数据，被调用方误认为真实结果；
- 超时后本地标记失败，但第三方实际成功；
- 依赖恢复后没有补偿积压机制。

### 验证设计

- 连接失败、慢响应、超时、限流和错误响应；
- 响应丢失但远端成功；
- 多层重试次数和总时延；
- 熔断打开、半开和恢复；
- 降级结果与业务语义；
- 依赖故障时的资源占用和背压；
- 恢复后的补偿、追赶和重复副作用防护。

---

## 八、安全与信任边界

### 需要回答

- 身份在哪里建立和验证；
- 授权是角色级、资源级、字段级还是租户级；
- 权限检查是否在所有入口和异步路径上成立；
- 调用方传入的用户、租户、角色或金额等字段是否被错误信任；
- 内部接口是否有独立的认证授权；
- 输入是否可能导致注入、路径遍历、不安全反序列化或 SSRF；
- 敏感数据是否会出现在响应、日志、Trace、指标、缓存或消息中；
- 密钥如何获取、轮换和限制权限；
- 审计记录是否能说明谁在何时做了什么；
- 数据保留、删除和脱敏要求是什么。

### 常见失败模式

- 只验证用户已登录，没有验证其能访问目标对象；
- 从请求体直接接受 tenantId 或 ownerId；
- 同步 API 有权限检查，后台任务和消息消费者没有；
- 管理接口只依赖“内网可达”；
- 缓存 Key 缺少权限或租户维度；
- 日志记录 Token、Cookie、身份证、银行卡或完整请求体；
- 错误信息暴露内部结构和敏感数据；
- 权限撤销后旧会话或缓存仍然有效。

### 验证设计

- 未认证、低权限、跨对象和跨租户访问；
- 同一资源的不同入口和异步入口；
- 字段篡改和服务端重新推导；
- 注入、路径、URL 和反序列化边界；
- 敏感数据在响应、日志、Trace、缓存和消息中的泄漏检查；
- 权限变更、撤销和缓存失效；
- 审计完整性和不可抵赖所需字段。

---

## 九、性能、容量与稳定性

### 需要回答

- 当前瓶颈由什么证据支持；
- 基线包含哪些延迟分位、吞吐、错误率和资源指标；
- 数据规模、并发、读写比、热点和请求分布是什么；
- 目标指标和可接受波动是什么；
- 优化是否改变行为、顺序、一致性或错误语义；
- 瓶颈在应用、数据库、缓存、网络、队列还是外部依赖；
- 资源上限和排队点在哪里；
- 限流、背压和过载保护如何工作；
- 优化在冷启动、缓存未命中和故障降级时是否仍成立；
- 新复杂度和运维成本是否值得。

### 常见失败模式

- 只测平均延迟，忽略尾延迟和错误率；
- 用小数据量微基准推断生产收益；
- 增加缓存后忽略一致性和失效成本；
- 增加并发后压垮数据库或下游；
- 批处理提高吞吐但扩大失败和重试范围；
- 为消除 N+1 加入超大查询，造成内存和锁问题；
- 优化正常路径，却让过载和依赖故障更严重；
- 没有回归门槛，无法判断收益是否真实。

### 验证设计

- 相同硬件、配置、数据和负载下的前后对比；
- 预热、冷启动、缓存命中和未命中场景；
- p50、p95、p99、吞吐、错误率和资源；
- 不同数据量、并发度和热点分布；
- 饱和点、排队、限流和恢复；
- 依赖变慢或失败时的稳定性；
- 长时间运行、连接池、内存和资源泄漏；
- 行为和数据语义回归。

## 十、时间、调度与后台任务

### 需要回答

- 时间使用 UTC、业务时区还是用户时区；
- 截止时间和区间边界是开区间还是闭区间；
- 夏令时、闰日、月末和时钟漂移是否相关；
- 任务可能由多个实例同时调度吗；
- 任务是否可重入、幂等和断点续跑；
- 错过执行后是补跑、跳过还是合并；
- 长任务如何分片、续租、超时和取消；
- 调度成功但执行失败如何区分；
- 失败、积压和处理进度如何观测；
- 手工补跑是否可能与正常调度并发。

### 常见失败模式

- 本地时间和 UTC 混用；
- 多实例重复执行同一批任务；
- 进程重启后从头执行并重复副作用；
- 调度器认为已提交即成功，实际处理失败；
- 月末、夏令时或跨日边界遗漏数据；
- 锁无租约，执行实例崩溃后永久占用；
- 补跑和正常任务同时处理相同对象。

### 验证设计

- 时区、跨日、月末、闰日和夏令时；
- 多实例竞争和租约过期；
- 任务中断、重启和断点恢复；
- 重复调度、手工补跑和并发执行；
- 空批次、大批次和单条异常；
- 调度、执行、成功、失败、积压和延迟指标。

## 十一、发布、可观测与清理

### 需要回答

- 是否需要 Feature Flag、灰度、影子流量或分阶段发布；
- 灰度维度是实例、租户、用户、流量比例还是数据分片；
- 发布前必须具备哪些日志、指标和 Trace；
- 哪些指标证明功能正确，哪些指标提示退化；
- 观察窗口和样本量是否足够；
- 什么条件继续扩大，什么条件立即停止或回滚；
- 回滚代码后数据、消息和外部副作用是否兼容；
- 如果不能直接回滚，前向修复和降级方案是什么；
- 临时双写、双读、开关、旧字段和兼容层何时清理；
- 谁确认迁移完成和消费者退出；
- 清理后如何验证没有隐藏依赖。

### 常见失败模式

- 只有技术错误率，没有业务正确性指标；
- 全量发布后才发现缺少关键日志和 Trace；
- 回滚代码但数据格式已经不可逆；
- Feature Flag 关闭只隐藏入口，没有停止后台副作用；
- 双写、兼容层和旧字段没有退出条件，永久存在；
- 灰度按实例，但同一业务对象跨新旧实例处理导致状态不一致；
- 指标改善是流量变化而非方案效果。

### 验证设计

- 发布前监控和告警可用性；
- 小范围灰度的功能、错误、延迟和业务不变量；
- 新旧版本同时运行；
- 开关开启、关闭和快速切换；
- 回滚代码或停止迁移后的数据可用性；
- 前向修复和人工处置流程；
- 临时机制清理前后的依赖扫描和回归验证。

## 使用本指南后的输出要求

风险分析不能只罗列“需要考虑事务、缓存、并发”等名词。对于每个被触发的风险，应给出：

```markdown
触发条件：
已验证事实：
可能失败的机制：
方案如何处理：
如何验证：
剩余风险或待确认事项：
```

如果证据证明某项风险不适用，应简要说明依据后停止，不继续扩展无关分析。
