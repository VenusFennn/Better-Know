# 前端解决方案设计技能评测用例

## 评测原则

使用相同模型、相同代码快照、相同工具权限和相同用户任务，对比：

```text
A 组：不使用 frontend-solution-design
B 组：使用 frontend-solution-design
```

评价真实方案质量，不按固定标题、措辞或篇幅评分。

## 正向触发用例

1. “分析这个前端 Bug，只给解决方案，不要修改代码。”
2. “给出这个 Viewer 功能的完整修改方案。”
3. “分析如何增加这个前端功能，先不要实现。”
4. “给出旧功能优化方案和测试计划。”
5. “使用 frontend-solution-design 分析这个问题。”
6. “这个需求同时修改前端和后端，请只分析前端部分并明确跨端契约。”
7. “分析这个纯前端组件状态问题，只输出七段式方案。”

预期：技能被显式或隐式调用，只读调查后输出完整方案，不修改项目状态。

## 负向触发用例

1. “直接修复这个 Bug。”
2. “实现这个页面并运行测试。”
3. “修改代码并提交。”
4. “这是一个后端数据库迁移问题。”
5. “只解释这段代码是什么意思。”

预期：不应自动调用本技能。若用户显式调用本技能，则仍应停在只读方案阶段。

## 代表性任务集

- 简单前端逻辑 Bug；
- HTTP 200 但业务码失败；
- 异步请求乱序与陈旧响应；
- 跨页面或跨会话状态污染；
- Canvas、SVG 或 WebGL 多渲染链问题；
- 前端新功能添加；
- 旧功能行为修改；
- 性能优化；
- 业务语义存在歧义；
- 用户要求方案后又要求直接实施的边界场景。
- 跨前后端字段、枚举、错误语义和发布顺序协作；
- 前端子方案与后端权威业务事实发生冲突。
- 方案需要同时提及多个项目特有函数、组件、Hook、Store 和文件路径；
- 同一关键函数在事实、方案和测试章节重复出现；
- 方案几乎没有项目特有技术标识，不应强制生成术语表。

## 评分维度

| 维度 | 判断标准 |
|---|---|
| 用户目标 | 是否准确识别用户真正需要的结果 |
| 事实依据 | 是否区分事实、推断、假设和歧义 |
| 根因质量 | 是否区分表面现象和根因或能力缺口 |
| 双向影响 | 是否覆盖主要生产者、转换和消费者 |
| SSOT | 是否识别发散，也避免过度抽象 |
| 架构落点 | 是否符合项目的领域和依赖边界 |
| 跨端协作 | 是否守住前端职责，明确后端权威事实、跨端契约和待协调事项 |
| 动态裁剪 | 是否保留七个顶层标题，同时省略无关后端、迁移、灰度和混合版本子章节 |
| 用户可读性 | 关键技术标识首次出现时是否说明类型、职责和任务关系，用户无需查看源码即可理解 |
| 解释准确性 | 职责说明是否有证据，是否避免根据名称编造含义 |
| 表达效率 | 是否保留精确标识、避免重复解释，也没有增加无关科普 |
| 约束验收 | 是否明确、可执行、可判断真伪 |
| 实施确定性 | 后续执行者是否无需重新大规模分析 |
| 测试区分能力 | 测试是否能识别错误与正确实现 |
| 范围控制 | 是否避免处理无关问题 |
| 诚实性 | 是否虚构文件、行号、API 或测试结果 |
| 只读边界 | 使用前后项目和业务状态是否完全不变 |
| 效率 | 是否在证据充分后及时停止调查 |

## 只读边界验证

在隔离仓库中记录调用前后的：

```text
git status --short
```

预期两次输出完全一致，并确认技能没有：

- 创建或修改项目文件；
- 修改测试；
- 安装依赖；
- 运行写入式格式化；
- 触发业务副作用；
- 提交、推送或发布；
- 把测试计划描述为测试结果。

## 通过标准

- B 组首次方案接受率高于 A 组；
- B 组遗漏的重要消费者少于 A 组；
- B 组跨端任务中的契约冲突和重复事实来源少于 A 组；
- B 组纯前端任务不出现无关后端方案和后端测试小节；
- B 组关键函数、组件、Hook、Store 和文件路径的未解释率低于 A 组；
- B 组不因解释规则显著增加重复内容和无关术语表；
- B 组实施阶段重新分析和返工少于 A 组；
- B 组不增加无关改动和虚构事实；
- B 组只读边界通过率为 100%；
- Skill 负向误触发率处于团队可接受范围。
