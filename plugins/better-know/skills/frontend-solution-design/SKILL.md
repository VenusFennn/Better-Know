# 前端解决方案设计

## 目标

基于只读调查，为前端 Bug 修复、新功能添加、旧功能修改和旧功能优化输出完整、正确、可执行、可验证的解决方案。

本技能只输出方案，不实施代码。技能被调用即表示当前任务停留在方案阶段；不得把方案阶段扩展为实现阶段。

## 不可违反的边界

允许：

- 阅读源码、项目文档、已有测试、日志、接口响应和 Git 历史；
- 搜索调用关系和数据流；
- 查看不会改变项目与业务状态的运行时证据；
- 执行不会写入项目、安装依赖或产生业务副作用的已有只读诊断。

禁止：

- 修改、创建、删除、格式化或批量重写项目文件；
- 修改测试文件；
- 安装或升级依赖；
- 修改配置、环境变量、数据库或业务数据；
- 执行具有业务副作用的操作；
- 提交、推送、发布、部署或创建 PR；
- 把计划中的实现或测试描述成已经完成；
- 因发现相邻问题而擅自扩大用户授权范围。

如果某项事实无法在只读条件下确认，将其明确标注为“待验证假设”，并说明它可能如何改变方案。

## 固定五步框架

0. 建立事实基线。
1. 双向分析上游生产者、中间转换和下游消费者。
2. 定义约束、非目标和验收标准。
3. 基于正确参考、项目架构与 SSOT 收敛原则设计完整方案。
4. 通过反证、边界推演和测试设计完成方案自验。

五步不可跳过，但每一步的分析深度应与用户影响、影响范围、不可逆性、系统复杂度和当前不确定性相匹配。

## 给方案前必答的五个问题

1. 要改什么、为什么改？
2. 它牵连哪些上游生产者、中间转换和下游消费者？
3. 有没有语义相同且经过验证的正确参考实现，是否需要收敛到权威来源？
4. 约束、非目标和验收标准是什么？
5. 哪些边界情况可能推翻方案，应如何验证？

五个问题必须得到实质回答，但不要求机械输出固定问答。简单任务可以合并表述，复杂任务应展开影响链、方案取舍和验证映射。

## 事实与证据纪律

明确区分：

- 已验证事实；
- 基于证据的推断；
- 为继续分析采用的工作假设；
- 尚未解决且会实质影响方案的歧义。

不得虚构文件、函数、行号、API、数据、需求、测试结果或 Git 历史。只有在源码或运行证据支持时，才能给出具体文件、符号和实施落点。

## 分析方式

- 优先使用当前项目的业务文档、API 契约、领域模型和架构规则；
- 参考既有实现前，先验证其业务语义、输入输出、约束和质量要求是否一致；
- 沿“上游生产者 → 中间转换与状态 → 变更对象 → 下游消费者”进行双向影响分析；
- 识别同一语义是否在多处重复维护，以及应收敛还是保持领域隔离；
- 调查到足以安全实施即可停止，不为了形式完整无限读取无关代码。

## 跨前后端协作

当任务同时涉及前端和后端时：

- 本技能只对前端领域给出专业子方案，不单独宣称已经完成全栈方案；
- 前端负责用户交互、浏览器端状态、请求消费、错误呈现、渲染和前端验证；
- 权限、金额、库存、所有权、领域状态合法性等权威业务事实原则上由后端领域拥有，前端只持有必要的输入、缓存和派生表示；
- API、事件、字段、枚举、错误语义和版本兼容属于跨端契约，不得由前端单方面假设或改变；
- 需要后端配合的内容必须明确写成契约要求、证据或待确认事项，不虚构后端实现；
- 与后端子方案出现冲突时，列出冲突、双方证据和收敛条件，不得忽略或任选一方；
- 跨端任务的统一结论、发布顺序和端到端验证交由 `fullstack-solution-design` 汇总。

建立跨端覆盖关系：

```text
用户需求
→ 前端改动
→ 跨端契约
→ 后端能力或约束
→ 联合验收与端到端验证
```

## 输出要求

最终方案根据任务复杂度调整篇幅，但必须覆盖：

1. 结论；
2. 事实、当前行为与根因或能力缺口；
3. 上游生产者、中间转换、下游消费者、隐性依赖和 SSOT；
4. 约束、非目标和可验证验收标准；
5. 推荐方案、架构落点、数据流或状态流及确定性实施步骤；
6. 测试与验证设计，包括正常、失败、边界和主要回归路径；
7. 具体风险、兼容与回滚思路，以及会实质影响实施的待确认事项。

跨前后端任务还必须输出前端职责、依赖的后端契约、兼容假设和需要全栈方案协调的事项。

建立“需求或问题 → 方案改动 → 验收标准 → 测试或验证”的覆盖关系。任何需求没有对应方案，或任何验收没有对应验证，都表示方案尚未完成。

## 测试设计责任

- 只设计测试，不修改测试文件，也不声称修复后测试已经通过；
- 根据失败模式选择单元、性质、组件、契约、集成、端到端、视觉、异步、故障注入或性能验证；
- Bug 回归测试在合理可行时应能体现“旧实现失败，按方案修复后通过”；
- 覆盖率用于发现遗漏，不单独证明测试质量；项目已有覆盖率门禁时必须在方案中遵守；
- 如某种测试不适用，说明原因和下一种最有区分能力的验证方式。

## 方案自验

输出前主动尝试推翻方案：

- 是否只修了下游症状；
- 是否遗漏重要生产者、转换或消费者；
- 是否错误复用了 Legacy 实现；
- 是否把后端权威业务事实复制成前端第二套事实来源；
- 是否对 API、事件、字段、枚举或错误语义作了未经后端证据支持的假设；
- 是否引入第二套事实来源、双轨状态或不必要兼容层；
- 是否遗漏竞态、缓存、生命周期、历史数据或质量属性；
- 是否存在更小但同样完整的方案；
- 是否依赖未经确认的业务假设；
- 测试是否真的能够识别目标错误。

## 停止规则

满足以下条件后停止调查并输出方案：

- 已能可靠解释当前状态、根因或能力缺口；
- 已形成足以安全实施的双向影响模型；
- 已明确权威来源、架构落点、约束、验收和关键边界；
- 已形成可执行的实施步骤和能够证明结果的测试设计；
- 进一步只读调查不太可能实质改变方案。

若仍缺少会实质改变产品语义、架构选择或不可逆风险的信息，提出最小且明确的待确认问题并停在方案阶段。
