# 方案可读性规范

> 1.0.0 · 业务含义优先 · 技术标识就地解释 · 保留精确定位 · 控制额外篇幅

## 一、目标读者

默认假设读者理解产品目标和业务场景，但不熟悉当前代码库的内部命名、分层和实现细节。

方案既要让用户理解“为什么这样改”，也要保留开发者实施所需的精确函数名、类名、字段名和文件路径。

用户明确要求专家简洁模式时，可以减少通用概念解释，但项目特有、职责不透明且影响方案理解的关键标识仍应在首次出现时说明。

## 二、什么需要解释

当以下内容对不了解代码库的读者不透明，并且它对现象、根因、影响或方案具有实质作用时，首次出现必须解释：

- 项目特有函数、方法、Hook、选择器和处理器；
- 项目特有类、组件、Service、Controller、Repository 和模块；
- 状态字段、业务字段、枚举和内部数据对象；
- 文件路径、表名、索引、Topic、队列和定时任务；
- API、RPC、事件和错误码；
- 缩写、架构模式和领域术语；
- 无法从普通中文语境直接理解的其它技术标识。

不需要机械解释：

- 已被用户主动使用并明确理解的术语；
- 与当前方案无关的代码对象；
- 后文重复出现且首次已经解释的同一标识；
- 解释不会增加任何有用信息的通用词汇。

判断标准不是“它看起来像代码”，而是“不了解当前项目的人能否知道它负责什么，以及为什么方案提到它”。

## 三、核心表达规则

### 规则 1：业务含义在前，技术标识在后

优先写：

```text
负责获取文件夹项目并更新页面状态的 `refreshFolderProjects` 函数
```

避免直接写：

```text
修改 `refreshFolderProjects`
```

当技术名称必须作为句子主语时，可以使用：

```text
`refreshFolderProjects`（负责获取当前文件夹项目并写入页面状态的函数）
```

### 规则 2：首次出现就地解释

解释应放在技术标识相邻位置，让读者不需要跳转到文末术语表。

首次解释至少回答：

1. 它是什么类型的对象；
2. 它负责什么；
3. 为什么与当前问题或方案有关。

不是所有对象都需要三句话。普通对象通常用一个短句同时表达类型和职责；根因核心对象再补充与问题的关系。

### 规则 3：解释实际职责，不翻译名称

不得把英文名称逐词翻译后当作解释。

例如，不能仅把 `OrderService` 解释成“订单服务”。应根据证据说明：

```text
封装订单确认、取消和状态推进规则的 `OrderService` 服务类
```

### 规则 4：解释必须受证据约束

职责说明优先依据：

- 源码实现；
- 调用关系；
- 测试；
- 业务和架构文档；
- API 或事件契约；
- 运行时证据。

如果只能推断，使用“从当前调用关系看”“根据现有命名和调用位置推测”等限定语。无法确认时标为待验证，不根据名称编造职责。

### 规则 5：说明与当前任务的关系

只说明对象的一般职责仍可能让用户不知道为什么要改它。

推荐：

```text
负责重新获取文件夹项目的 `refreshFolderProjects` 函数。问题与它有关，是因为它会把接口响应直接写入当前页面状态，却没有判断响应是否已经过期。
```

### 规则 6：保留精确技术标识

通俗解释不能代替真实名称。函数、类、文件、字段、接口、表和 Topic 的原始标识应保留在反引号中，便于开发者搜索和实施。

### 规则 7：首次完整解释，后续使用中文短称

第一次：

```text
负责刷新文件夹项目的 `refreshFolderProjects` 函数（下文简称“文件夹刷新逻辑”）
```

后续：

```text
文件夹刷新逻辑收到旧响应时，应丢弃该响应。
```

只出现一次的标识不需要专门声明简称。

### 规则 8：解释密度必须可控

当少量技术对象分散出现时，使用行内解释。

当多个关键对象集中出现、继续使用括号会打断阅读时，在当前相关章节内动态增加“关键对象说明”小节：

```markdown
### 关键对象说明

| 技术对象 | 类型 | 通俗作用 | 与本任务的关系 |
|---|---|---|---|
| `refreshFolderProjects` | 函数 | 获取文件夹项目并更新页面状态 | 旧响应会在这里覆盖新数据 |
| `FolderProjectList` | 组件 | 把文件夹项目渲染成列表 | 只展示已经加载的数据 |
```

该小节不是固定模板，不得为了形式完整列出整个项目的对象字典。

## 四、不同技术对象的表达方式

### 函数和方法

```text
负责校验订单能否确认并推进状态的 `OrderService.confirm` 方法
```

### 类、组件和模块

```text
负责展示上传进度以及暂停、继续和删除操作的 `UploadProgressDialog` 组件
```

### Hook、Store 和状态容器

```text
统一管理文件夹详情数据、加载状态和接口请求的 `useProjectFolderWorkspace` Hook（可复用的前端状态逻辑）
```

### 文件路径

不能裸列路径。说明文件职责：

```text
问题位于上传进度弹窗组件文件 `src/widgets/upload/progress/ui/UploadProgressDialog.jsx`，该文件负责展示任务状态并连接暂停、继续和删除交互。
```

### 字段和枚举

```text
`projectStatus` 字段（表示项目当前处于上传、暂停、成功还是失败阶段）
```

### API 和事件

```text
用于确认指定订单的 `POST /orders/{id}/confirm` 接口
```

```text
表示“订单已经确认”的 `OrderConfirmed` 事件，库存和通知服务会消费它执行后续处理
```

### 表、索引和 Topic

```text
保存待发送领域事件的 `outbox_events` 表，用于保证业务数据提交后消息最终能够发出
```

### 缩写和专业术语

第一次同时给出中文含义和本任务中的作用：

```text
单一事实来源（SSOT），即同一业务事实只有一个权威维护位置
```

```text
Outbox（待发送事件表模式），用于避免数据库提交成功但消息没有发出的不一致
```

## 五、七段式中的放置规则

不增加新的固定顶层章节。解释嵌入既有七段式：

### 1. 结论

以用户目标、问题本质和推荐方案为主。除非某个技术对象是理解结论不可缺少的核心，否则不在结论中堆叠代码名称。

### 2. 事实与根因

解释导致现象的关键函数、类、模块、字段和数据对象。多个对象集中出现时，可在本节动态增加“关键对象说明”。

### 3. 双向影响面

说明生产者、中间转换、状态、副作用和消费者的通俗职责，再给出精确技术标识。

### 4. 约束、非目标和验收标准

优先使用可观察结果，不使用函数名代替验收标准。

### 5. 详细解决方案

解释每个主要修改对象当前职责、目标职责和它在方案中的位置。不得只给文件与函数清单。

### 6. 测试与验证方案

提到测试文件、测试函数、Mock、Fixture 或工具时，说明它验证什么失败模式。不得只列测试文件名。

### 7. 风险与待确认事项

使用业务和系统影响描述风险。技术标识只用于准确定位，不应成为风险描述主体。

## 六、前后端与全栈协调

### 前端方案

重点解释组件、Hook、Store、选择器、事件处理器、渲染器和浏览器状态的职责。DOM、Canvas、SVG、WebGL 等术语第一次出现时说明其在当前功能中的作用。

### 后端方案

重点解释 Controller、Service、Repository、领域对象、数据库表、Topic、任务和外部依赖的职责。事务、幂等、Outbox、Saga、CQRS 等术语必须说明它们解决的具体业务或故障问题。

### 全栈方案

同一个技术对象在统一输出中只完整解释一次。前端和后端存在同名或相似对象时，必须说明所属层和职责差异。跨端字段和枚举应解释业务语义、生产者和消费者。

不得直接拼接两个子方案中的重复解释。

## 七、自适应规则

- 没有晦涩技术标识时，不生成“关键对象说明”；
- 简单任务使用短句解释，不扩展成教程；
- 复杂任务按局部主题分组解释，不集中生成与上下文脱节的长词典；
- 用户明确要求精简时，减少通用术语解释，但保留关键项目标识的职责说明；
- 用户要求面向非技术人员时，进一步减少实现细节，仍保留少量必要定位；
- 用户要求面向实施开发者时，保留更多精确标识，但不取消首次职责解释。

## 八、可读性质量门禁

输出前检查：

- [ ] 用户可感知现象和业务目标先于代码定位；
- [ ] 每个关键且不透明的技术标识首次出现时都有相邻解释；
- [ ] 解释说明了对象类型、职责，以及必要时与当前任务的关系；
- [ ] 文件路径、函数名和类名没有裸列；
- [ ] 缩写和专业术语首次出现时已有中文含义；
- [ ] 解释来自证据，推断已明确标注；
- [ ] 精确技术标识仍然保留并可搜索；
- [ ] 重复出现时使用稳定中文短称，没有反复解释；
- [ ] 没有为了通俗而删除关键约束或改变技术语义；
- [ ] 没有为了可读性增加无关科普、空小节或整库术语表；
- [ ] 七个顶层章节和动态子章节规则保持不变。

## 九、停止规则

当读者无需查看源码即可回答以下问题时，可读性处理已经足够：

1. 被提到的关键对象大致负责什么；
2. 为什么当前方案需要提到或修改它；
3. 它与上游、下游或用户现象有什么关系。

满足后停止补充解释，不继续扩展无关背景知识。
