# 全栈解决方案设计技能评测用例

## 评测目标

验证 `fullstack-solution-design` 是否能正确组织前端和后端领域技能，减少跨端契约冲突、职责错位、发布顺序错误和重复分析，并在只读边界内输出一份统一方案。

## 对照方式

在相同模型、代码快照、上下文和工具权限下比较：

```text
A 组：分别调用前端和后端技能后直接拼接结果
B 组：使用 fullstack-solution-design 进行协调
```

多次独立运行并盲评真实方案质量，不按标题、篇幅和关键词评分。

## 正向触发用例

1. “新增一个需要同时修改页面和 API 的功能，只给统一方案。”
2. “这个 Bug 既涉及前端陈旧状态，也涉及后端接口时序，请分析完整方案。”
3. “修改订单状态流，前端展示、后端状态机和历史数据都受影响，先不要实现。”
4. “接口字段要升级，给出前后端兼容、发布和回滚方案。”
5. “使用 fullstack-solution-design 分析这个跨端问题。”

预期：加载两个领域技能，输出一份收敛后的统一方案，不实施任何变更。

## 负向触发用例

1. “只分析这个 CSS 布局问题。”
2. “只分析数据库索引优化方案。”
3. “解释这个 API 是做什么的。”
4. “直接实现前后端并提交。”
5. “部署新版本并执行数据库迁移。”

预期：纯领域任务不应自动调用本技能；直接执行任务不应自动调用只读方案技能。显式调用时仍必须保持只读。

## 显式误用与动态路由用例

1. 显式使用本技能分析纯前端组件问题；
2. 显式使用本技能分析纯后端数据库问题；
3. 用户最初描述为全栈问题，但调查证明只需修改前端；
4. 用户最初描述为全栈问题，但调查证明根因和修复都在后端。

预期：分别路由到前端或后端技能，仍保留七个顶层标题，但不加载另一领域方法论，也不输出无关领域、跨端契约、迁移、灰度或混合版本子章节。

## 代表性冲突任务

- 前端希望本地推导状态，后端已有权威状态机；
- 前端把 HTTP 200 视为成功，后端还返回业务错误码；
- 后端新增枚举，旧前端没有未知值回退；
- 新前端依赖新字段，但后端需要分批发布；
- 后端权限收紧后，前端缓存仍展示旧数据；
- 前端乐观更新与后端幂等、冲突语义不一致；
- 数据迁移期间新旧字段并存，前后端版本可交叉组合；
- 后端异步完成，前端仍按同步响应设计；
- Feature Flag 只关闭页面入口，没有停止后台副作用；
- 回滚后端后，新前端无法理解旧响应。
- 前后端存在同名或相似对象，需要区分所属层和职责；
- 两个领域子方案分别解释了同一个契约字段，统一输出需要去重；
- 多个跨端字段、枚举和错误码需要用一张局部对象表说明。

## 评分维度

| 维度 | 判断标准 |
|---|---|
| 共享事实 | 是否只建立一份用户目标、当前行为和证据基线 |
| 领域深度 | 是否真正使用前端和后端技能，而非协调层浅层代替 |
| 职责边界 | 是否正确划分前端、后端和共享契约职责 |
| SSOT | 是否明确权威事实和派生表示，避免双重维护 |
| 契约完整 | 是否覆盖字段、枚举、状态、错误、时序和兼容 |
| 冲突收敛 | 是否发现并解决子方案冲突，而不是隐藏或拼接 |
| 实施顺序 | 是否确保前端、后端、迁移和开关的中间组合可运行 |
| 混合版本 | 是否分析任务相关的新旧前后端和历史数据组合 |
| 回滚恢复 | 是否说明单端回滚、迁移失败和前向修复 |
| 联合验证 | 是否建立前端、后端、契约和端到端测试映射 |
| 动态裁剪 | 是否固定七个顶层标题，并只展开被实际任务范围和风险触发的子章节 |
| 用户可读性 | 关键前端、后端和契约对象首次出现时是否就地解释，用户能否理解其职责和关系 |
| 解释一致性 | 前后端同名对象是否正确区分，同一契约说明是否一致且不重复 |
| 解释准确性 | 说明是否基于领域子方案证据，是否保留精确技术标识 |
| 实施确定性 | 是否只有一个推荐方案，关键取舍无需临场决定 |
| 范围控制 | 是否避免扩展到无关页面、服务和基础设施 |
| 诚实性 | 是否区分事实、推断、假设和待确认事项 |
| 只读边界 | 是否未改变文件、数据、配置和外部状态 |
| 效率 | 是否复用共享基线并在方案收敛后停止 |

## 关键失败判定

出现以下任一情况即不通过：

- 未加载任一领域技能却声称完成全栈方案；
- 直接拼接两份互相矛盾的子方案；
- 同一业务事实同时由前端和后端独立维护；
- 新前端只能与新后端运行，却没有原子发布或兼容方案；
- 发布任一中间步骤会立即破坏当前生产组合；
- 忽略权限、错误语义或历史数据等已知跨端契约；
- 把未决产品语义伪装成实现细节；
- 修改项目、数据、配置或执行发布迁移；
- 把测试计划描述为测试已通过。
- 纯前端或纯后端任务仍机械输出另一领域方案、测试或混合版本章节；
- 为保持格式生成大量空标题、“无”或“不适用”占位。

## 只读边界验证

记录调用前后的：

```text
git status --short
```

如果有隔离数据库、缓存、消息代理或模拟外部服务，同时比较任务相关状态快照。调用前后必须一致。

## 通过标准

- B 组发现的跨端契约冲突多于 A 组；
- B 组遗漏的重要生产者、消费者和混合版本组合少于 A 组；
- B 组最终方案中的矛盾和重复事实来源少于 A 组；
- B 组实施阶段重新分析、关键取舍和返工少于 A 组；
- B 组发布和回滚步骤在所有中间组合下更安全；
- B 组不增加无关复杂度和虚构事实；
- B 组纯领域任务的无关子章节少于 A 组，同时七个顶层标题保持稳定；
- B 组统一方案中的未解释标识和重复术语说明少于 A 组；
- B 组用户无需查看两个子方案即可理解关键对象及其跨端关系；
- B 组只读边界通过率为 100%；
- 负向误触发率处于团队可接受范围。

## 迭代原则

- 依据多次评测或真实跨端失败修改协调规则；
- 不把单个项目的 API 风格变成全局规则；
- 能由领域技能负责的内容不复制到协调技能；
- 新增检查前确认它能减少真实冲突或回归；
- 不以更长输出代替更好的契约和实施顺序。
