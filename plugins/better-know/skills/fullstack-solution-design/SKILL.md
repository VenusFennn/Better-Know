# 全栈解决方案设计

## 目标

为同时涉及前端和后端的变更建立共享事实基线，组织前端与后端领域分析，消解契约和职责冲突，输出一个可实施、可验证、发布与回滚顺序清晰的统一解决方案。

本技能是协调层，不替代或复制两个领域技能：

- `frontend-solution-design` 负责前端领域子方案；
- `backend-solution-design` 负责后端领域子方案；
- 本技能负责跨端契约、职责收敛、实施顺序和联合验证。

## 不可违反的边界

本技能只读分析并输出方案。允许读取前后端源码、契约、文档、测试、脱敏日志、运行时证据和 Git 历史；禁止修改项目、测试、配置、数据、缓存、消息和外部系统状态，禁止安装依赖、迁移、提交、发布或部署，也不得把计划描述成已完成事实。

若证据不足，应区分事实、推断、工作假设和歧义。会改变业务语义、契约、数据模型、迁移或不可逆风险的歧义必须提出最小待确认问题。

## 依赖技能

每次使用本技能时，先判断实际变更范围：

1. 纯前端任务只加载并遵循 `frontend-solution-design`，不加载后端技能；
2. 纯后端任务只加载并遵循 `backend-solution-design`，不加载前端技能；
3. 真正跨前后端的任务必须同时加载并遵循两个领域技能；
4. 跨端协调时必须完整读取 [全栈解决方案协调方法论](references/全栈解决方案协调方法论.md)；
5. 只把领域技能的分析结果作为统一方案输入，不把多份输出原样拼接。

在 Codex 中对应 `$frontend-solution-design` 和 `$backend-solution-design`；在 Better Know 的 Claude Code 插件中对应 `/better-know:frontend-solution-design` 和 `/better-know:backend-solution-design`。

如果实际任务所需的领域技能不可用，明确报告缺失依赖并停止，不临时编造或内联替代完整领域方法论。

评价或回归测试本技能时读取 [技能评测用例](references/技能评测用例.md)；打包或验证完整性时读取 [内容覆盖清单](references/内容覆盖清单.md)。

## 固定五步框架

0. 建立共享事实基线：统一用户目标、当前行为、目标行为、证据、业务不变量和歧义。
1. 领域拆分与双向分析：分别形成前端子方案、后端子方案和跨端依赖图。
2. 契约与验收收敛：确定权威事实、请求响应、事件、字段、枚举、错误语义、兼容和联合验收。
3. 统一方案设计：整合职责、实施步骤、迁移、Feature Flag、发布顺序、观测、回滚和清理。
4. 联合自验：通过冲突审查、故障推演、混合版本推演和分层测试映射证明方案完整。

五步不可跳过，但分析深度应与用户影响、跨端范围、数据风险、不可逆性、系统复杂度和不确定性相匹配。

## 给统一方案前必答的五个问题

1. 用户要完成什么端到端目标，当前链路为什么不能满足？
2. 哪些事实和行为分别由前端、后端或跨端契约拥有？
3. 请求、响应、事件、字段、枚举、状态和错误语义应如何收敛，SSOT 在哪里？
4. 新旧前端、新旧后端、历史数据、迁移和 Feature Flag 如何兼容，发布与回滚顺序是什么？
5. 哪些跨端边界、失败和混合版本场景可能推翻方案，如何通过领域测试、契约测试和端到端测试验证？

五个问题必须得到实质回答，不要求机械输出固定问答。

## 职责判定

通常按以下原则收敛，但项目证据和业务契约优先：

- 前端拥有交互流程、浏览器端临时状态、请求消费、错误呈现和渲染表示；
- 后端拥有领域不变量、权威业务规则、权限、数据、事务和外部副作用；
- API、事件、字段、枚举、状态映射、错误语义和兼容窗口属于跨端契约；
- 前端可以为即时反馈重复部分校验，但后端仍执行权威校验，且两者应派生自同一契约或规则来源；
- 不能依据技术偏好决定所有权，必须依据业务语义、信任边界、数据权威和现有架构。

## 冲突处理

当前端与后端子方案不一致时：

1. 明确冲突对象和双方假设；
2. 回到用户目标、业务要求、现有契约、领域模型、运行证据和兼容约束；
3. 判断是职责错位、契约歧义、事实不一致还是方案取舍；
4. 能由证据决定时给出唯一推荐；
5. 需要产品决定时提出最小问题并说明不同答案如何改变方案；
6. 不得把相反方案同时交给实施者自行选择。

## 输出要求

无论任务最终被路由为前端、后端还是跨端，输出都必须保留以下七个顶层标题：

1. 结论；
2. 事实与根因；
3. 双向影响面；
4. 约束、非目标和验收标准；
5. 详细解决方案；
6. 测试与验证方案；
7. 风险与待确认事项。

七个顶层标题固定，二级及以下内容按任务范围动态生成：

- 纯前端任务在七段式内只呈现前端相关内容，不输出后端影响、后端方案、后端测试、跨端契约、迁移、混合版本或联合发布等无关小节；
- 纯后端任务在七段式内只呈现后端相关内容，不输出前端影响、前端方案、前端测试或跨端发布等无关小节；
- 真正跨端任务才在“详细解决方案”中展开前端方案、后端方案、跨端契约、冲突收敛和统一实施顺序，并在“测试与验证方案”中展开前端、后端、契约和端到端验证；
- 数据迁移、Feature Flag、灰度、回滚、混合版本和临时机制清理只在任务确实触发这些风险时出现；
- 不输出空二级标题，也不使用批量“无”“不适用”占位；固定顶层章节内容较少时，用有实质信息的一段话表达。

跨端任务的七段式必须实质覆盖：

- 共享事实、目标、根因或能力缺口；
- 前端职责与改动；
- 后端职责与改动；
- 跨端契约、SSOT、兼容和冲突收敛结果；
- 实施、迁移、Feature Flag、灰度、清理和回滚的必要顺序；
- 正常、失败、边界、混合版本和主要回归路径；
- 前端、后端、契约和端到端测试的责任映射；
- 具体风险和会实质影响实施的待确认事项。

建立完整覆盖关系：

```text
用户需求
→ 前端改动
→ 跨端契约
→ 后端改动
→ 发布与迁移步骤
→ 验收标准
→ 分层测试与端到端验证
```

任何需求没有对应方案、任何契约没有明确生产者和消费者、任何验收没有对应验证，都表示统一方案尚未完成。

## 联合自验

输出前主动检查：

- 是否只是拼接两份子方案；
- 是否存在前后端对同一字段、枚举、状态或错误语义的不同理解；
- 是否在前端复制后端权威业务事实；
- 是否把具体 UI 表现错误地固化为后端领域规则；
- 是否遗漏旧前端、新前端、旧后端、新后端的交叉兼容；
- 是否遗漏历史数据、缓存、消息或后台任务；
- 发布顺序中是否存在任一步上线后立即破坏当前生产组合；
- 回滚任一端后系统是否仍能工作；
- 契约测试是否能发现双方独立实现但语义不一致；
- 端到端测试是否只覆盖成功路径；
- 是否存在更小但同样完整的跨端方案；
- 是否有关键取舍仍被留给实施者临场决定。
- 是否为纯前端或纯后端任务输出了另一领域的空泛章节；
- 是否把未触发的迁移、灰度、回滚或混合版本检查机械写入方案。

## 停止规则

满足以下条件后停止调查并输出方案：

- 共享事实和目标已明确；
- 前端、后端和跨端契约职责已收敛；
- 子方案冲突已有结论或最小待确认问题；
- 新旧版本、迁移、发布、观测和回滚顺序可执行；
- 联合验收和分层测试能够证明结果；
- 进一步调查不太可能实质改变统一方案。

不得为了展示全面而扩展到无因果关系的服务、页面和基础设施。
